# 한국어 문서 Q&A 검색 (RAG 검색 파이프라인)

질문을 넣으면 문서 묶음에서 답의 근거가 되는 문단을 찾아 주는 RAG의 검색(Retrieval) 단계 구현과 성능 실험입니다.
청크 크기와 검색 방식(BM25 / 벡터 / 하이브리드)을 바꿔 가며 정답 문단을 얼마나 위쪽에서 찾는지 Hit@k와 MRR로 비교했습니다.

## 왜 만들었나

졸업작품 LogiIQ의 AI 캐릭터는 프로젝트 정보를 모른 채 답해서 엉뚱한 답을 할 때가 있었습니다.
답을 만들기 전에 근거 문서를 먼저 찾아 붙여 주는 RAG가 해법이라고 보고, 그중 결과를 가장 크게 좌우하는 검색 단계를 직접 만들고 숫자로 확인했습니다.

## 구조

```
문서 140편 ─ 청크 나누기(300/600/1000자, 20% 겹침) ─┬─ BM25 색인 (글자 2개 단위)
                                                    └─ 임베딩(multilingual-e5-small) → Qdrant
질문 ─┬─ BM25 상위 50 ─┐
      └─ 벡터 상위 50 ─┴─ 순위 합치기(RRF) → 상위 k개 근거 문단
```

| 파일 | 하는 일 |
|---|---|
| `src/data_prep.py` | KorQuAD 1.0 dev를 내려받아 문서 140편과 평가 질문 500개로 정리. 정답의 문서 내 위치를 같이 저장 |
| `src/chunking.py` | 문장 끝에서 끊으며 글자 수 기준으로 청크 분할, 앞 청크와 20% 겹침 |
| `src/embedder.py` | e5 임베딩(질문엔 `query:`, 문서엔 `passage:` 접두어) / 글자 n-gram 해시 기준선 |
| `src/retriever.py` | BM25, Qdrant 벡터 검색, RRF 하이브리드 |
| `src/evaluate.py` | 청크 크기 × 검색 방식 조합별 Hit@1, Hit@5, MRR@10, 질문당 검색 시간 측정 |
| `app.py` | Streamlit 화면. 질문하면 근거 문단과 정답 위치를 표시 |

## 실행

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python src/data_prep.py                 # 데이터 내려받기·정리
python src/evaluate.py --embedder e5    # 실험 (처음엔 모델 다운로드로 몇 분 걸림)
streamlit run app.py                    # 화면
```

## 평가 방법

- 데이터: KorQuAD 1.0 dev, 위키 문서 140편(약 52만 자), 질문 500개(무작위, seed 42)
- 맞힘 기준: 정답 문자열의 문서 내 위치를 포함하는 청크를 찾아오면 정답
- Hit@k: 상위 k개 안에 정답 청크가 있는 질문 비율 / MRR@10: 정답 청크 순위의 역수 평균

## 결과

질문 500개, 맥(arm64) CPU, Python 3.14에서 `bash run_all.sh`로 측정했습니다. 원본 표는 `results/` 폴더에 있습니다.

**e5 임베딩 (multilingual-e5-small)**

| 청크 크기 | 검색 방식 | Hit@1 | Hit@5 | MRR@10 | ms/질문 |
|---|---|---|---|---|---|
| 300 | BM25 | 0.826 | 0.966 | 0.887 | 5.6 |
| 300 | 벡터 | 0.720 | 0.912 | 0.803 | 12.8 |
| 300 | 하이브리드 | 0.802 | 0.952 | 0.873 | 16.9 |
| 600 | BM25 | 0.890 | 0.984 | 0.931 | 2.5 |
| 600 | 벡터 | 0.720 | 0.924 | 0.807 | 9.2 |
| 600 | 하이브리드 | 0.822 | 0.976 | 0.889 | 12.3 |
| 1000 | BM25 | **0.894** | **0.986** | **0.936** | 1.2 |
| 1000 | 벡터 | 0.708 | 0.930 | 0.804 | 8.9 |
| 1000 | 하이브리드 | 0.850 | 0.978 | 0.907 | 10.4 |

**벡터 검색만 비교 (MRR@10)**

| 청크 크기 | 글자 해시 기준선 | e5 |
|---|---|---|
| 300 | 0.681 | 0.803 |
| 600 | 0.670 | 0.807 |
| 1000 | 0.650 | 0.804 |

## 배운 점과 다음 단계

- 모든 조합에서 BM25가 가장 좋았습니다(1000자 청크에서 MRR 0.936). KorQuAD는 지문을 보고 질문을 만든 데이터라 질문과 정답 문단의 단어가 많이 겹치고, 그래서 키워드 검색이 유리했던 것으로 봅니다. 실제 사용자 질문처럼 표현이 다른 경우에도 같은 결과가 나올지는 따로 확인해야 합니다.
- 벡터 검색끼리 보면 e5가 글자 해시 기준선보다 MRR이 0.12~0.15 높았습니다. 임베딩 모델이 글자 겹침 이상의 의미를 잡는다는 건 확인했지만, 이 데이터에서는 BM25를 넘지 못했습니다.
- 하이브리드(RRF)는 벡터 단독보다는 좋았지만 BM25 단독보다는 낮았습니다. 두 결과를 같은 비중으로 합치면 약한 쪽이 순위를 끌어내릴 수 있어서, 비중을 조절하는 실험이 필요합니다.
- 청크가 클수록 점수가 올랐는데, 청크가 크면 정답 위치를 포함하기 쉬워지는 영향도 있습니다. 대신 LLM에 넘길 글이 길어지므로 실제 답변 생성까지 붙여서 다시 비교해야 합니다.

- 다음 단계: 찾은 문단을 LLM에 넘겨 답변 문장 생성, 질문을 다르게 바꿔 쓴(패러프레이즈) 평가 세트로 재실험, 재정렬(re-ranker) 추가
